# 首次报价和余额读取复测

本次对比基线为 PR #3 上轮提交 `5fa2a319602cfc6ae7b0297bdfd8944b26fdc5f7`。报价测试为 0.001 BNB→USDT，滑点 0.5%，多跳开启。余额批量查询 BNB、USDT 和 FIST。

## 12.86 秒样本

上轮 PublicNode 原始记录中，BNB→USDT 的冷报价耗时 **12,855.70 ms**，全部 15 次 HTTP 返回 200，包含 493 个合约子调用。以下是同一请求的墙钟阶段。Oracle、V2 与 V3 发现并行，不能把这些阶段和 RPC 耗时相加。

| 阶段 | 耗时 | 请求细节 |
|---|---:|---|
| 初始链验证及最新头 | 699 ms | 两次顺序 HTTP |
| 配置与准入上下文（含最新头，不含初始链验证） | 6,926 ms | 配置与其内部链检查并行 |
| 其中池准入 | 6,173 ms | Oracle、V2、V3 发现后等待 V3 状态和深度 |
| 其中 V3 状态 | 3,259 ms | 240 子调用，三批并行，最慢约 3.19 秒 |
| 其中 V3 深度 | 1,712 ms | 74 子调用，一批 |
| 路线金额计算 | 4,808 ms | 顺序的三层分别约 1,851、1,431、1,492 ms，共 66 子调用 |
| 最终区块核对 | 773 ms | 路线读完后，核对同一高度的 hash |
| 转账税模型读取 | 0.06 ms | 该样本的参与代币走既有税模型 |

实际 HTTP 工作的时间窗联合覆盖约 **12,741 ms（99.1%）**，包含节点执行、传输和客户端读响应体。现有阶段数据无法进一步分开节点内部执行与传输。三层金额计算的每层批次分别只有 19、27、20 项，因此每层最多两批的上一轮改动在这里没有额外并行机会。原记录见 [PublicNode trace](critical-read-performance-20261122/publicnode.json.gz)。

## 改动

- 冷余额和冷报价把 `eth_chainId` 与最新头放在同一个二项 JSON-RPC 批次，验证 BSC 后才使用头。余额仍在该高度重新读取并核对 hash。报价在完成路线计算后再次核对同一高度的 hash。
- 余额需要新头且加入更早启动的链验证时，只复用链验证，另读自己的最新头。节点不支持 batch 时按原顺序读取，链证明年龄仍从链 ID 检查完成时起算。错误链批次不写入节点头指标。
- 当整个币对查询的代币图来自主流币集合且两侧独立价格有效时，保留原有 V3 状态读取，只跳过已经被现有价格对齐或双边流动性门槛拒绝的池的深度模拟。仍有资格的池保留原来的双向 500 美元深度探测。混合代币图保留原检查方式。
- 阶段计时新增 `bootstrap`。基准同时记录物理 HTTP、JSON-RPC 项数和合约子调用数，避免把同一 HTTP 中的两项重复当作两轮。

## 最终源码实测

本地引擎直接访问公开 BSC PublicNode。每个配对固定到该组取得的真实区块，两侧仍请求最新头的基准对应项、检查实际 canonical hash、使用真实时钟和原有效期。冷指新引擎和新 provider pool，进程和网络连接可能已经复用。预热前后使用独立引擎，单币对预热耗时单列。在预热后输入 0.001 BNB，再改为 0.0011 BNB。余额进行了两组配对并交替先后，BNB 报价进行了最终源码一组配对。两轮节点试测的原始结果都已保留，选 PublicNode 的依据是当时四次区块头探测的整体时间，该选择不代表长期排名。

| 场景 | 基线 → 最终源码 | HTTP | JSON-RPC 项 | 合约子调用 |
|---|---:|---:|---:|---:|
| 冷余额 A | 1,452.01 → 705.66 ms | **3 → 2** | 4 → 4 | 3 → 3 |
| 冷余额 B | 3,438.85 → 1,164.07 ms | **3 → 2** | 4 → 4 | 3 → 3 |
| 已验链后强制刷新余额 A | 742.85 → 739.84 ms | 2 → 2 | 3 → 3 | 3 → 3 |
| 已验链后强制刷新余额 B | 1,585.99 → 3,392.87 ms | 2 → 2 | 3 → 3 | 3 → 3 |
| 冷报价 | 6,397.08 → 5,017.48 ms | **15 → 14** | 15 → 15 | **493 → 453** |
| 单币对预热成本 | 3,646.64 → 5,172.93 ms | 12 → 12 | 12 → 12 | 427 → 387 |
| 预热后首次报价 | 3,848.80 → 1,522.79 ms | 4 → 4 | 4 → 4 | 66 → 66 |
| 预热后改金额 | 1,513.54 → 1,534.73 ms | 4 → 4 | 4 → 4 | 66 → 66 |

最后版本 16/16 操作有效，8 组配对中适用的区块 hash、余额、输出、最低到账、手续费和所选路线全部一致。两份记录中候选关键源码哈希与提交内容一致。V3 的 240 个状态子调用不变，冷报价的深度探测由 **74 → 34**，路线计算仍为 66 个子调用和 51 个有效候选。现有 500ms 余额头缓存及原截止时间保持原约束。

**首次报价尚未达到 1 秒目标。**本次确认减少了冷路径工作量。提交前的稳定前序版本（仅缺普通余额并发修正，顺序报价逻辑相同）两组冷报价分别为 **4.33 → 4.53 秒** 和 **4.53 → 5.55 秒**，请求数同样少一轮。预热后改金额出现 **4.09 秒** 和 **3.86 秒** 的候选样本，均命中上下文，无新配置或池扫描。前者的三层 route RPC 分别约 2,034、1,325、357 ms，后者约 1,099、1,618、573 ms，再分别花 342 和 494 ms 核对区块。四次公网 RPC 响应构成主要耗时。此次公网记录属于本地引擎调用，样本量不足以估计生产尾延迟，也没有测浏览器端到端。

链证明已缓存而 500ms 头缓存未命中时仍需要两次 HTTP。节点不支持批量读时会回到顺序读取，不能套用 3 → 2 的结果。报告保留两轮正式前序数据，其中首次测试期间有源码修改，工具因哈希不一致返回失败，该轮单列，最终结论使用稳定源码。
